# Fresh pruned-receiver issuance authentication

November 23, 2026. Design for owner review. No consensus activation.

## Trust boundary

The current selected-child verifier checks the stored header, GHOSTDAG selected parent and transaction Merkle root before reading the coinbase. Header hashing commits to the transaction root, accepted-ID root, UTXO root and pruning point. The shielded verifier authenticates the shielded state root. None of these fields independently commits to historical minting, selected reward-source attribution or deferred developer liability. A peer can transport a checkpoint and a child body. The receiver must derive the expected issuance digest from independently accepted chain evidence before inspecting that checkpoint as an issuance proof.

Local replay is a separate source of evidence. It uses the locally validated settlement history and compares the supplied path to both directions of the persisted selected index under its authoritative guard. A retained local anchor can survive index pruning on that same node.

Recommend evaluating the coinbase extension first. The repository already verifies selected-child body membership and reads a commitment from that coinbase. Commit the digest for the **selected parent** (the target pruning point), through its settled state inclusive. Binding the containing block's own hash or that block's own settlement into the field would risk a hash cycle. At activation, validators must reconstruct the selected-parent digest from authenticated consensus accounting before accepting the child. An IBD proof authenticates selected chain evidence under the network's bootstrap assumptions; it does not replay historical settlement for the receiver. The owner must approve the trust assumptions used to cross activation, especially a node with no retained local history.

## Candidate v1 semantics

Reuse `IssuanceCheckpoint::commitment`. Its domain is the ASCII bytes `KASCADE/issuance-checkpoint/v1`, hashed using the existing `kaspa_hashes::TransactionHash` convention. Append network genesis hash, target pruning point hash and ordered event root as three fixed 32-byte values, then claim count, cumulative minted, paid and deferred as four unsigned 64-bit little-endian values. Amounts are in atomic units. This defines the digest preimage. The consensus wire envelope still requires approval. Specify an explicit version selector and 32-byte digest, require an exact canonical representation, reject missing, duplicate or unknown active versions, and forbid falling back to an unauthenticated version after activation.

The two existing leaf domains are `KASCADE/issuance-claim/v1` and `KASCADE/issuance-developer-release/v1`. Bind each leaf to the selected block hash and selected index. Order claims by selected index then source hash, followed by the single allowed release at that index. Claim leaves bind reward source, minted and paid. Release leaves bind the amount drawn from the developer liability. A release reduces deferred and increases paid by the same amount. Validate actual fee-only red-block accounting before constructing claims, and exclude fees from issued supply. Check unique sources, selected ancestry, at most one release per selected block, checked arithmetic, liability sufficiency, and minted = paid + deferred. The proposed aggregate limit is 29B KCADE, with 21B primary and 8B finite tail; the proposed phase budgets and cutoff require a separately validated schedule and activation. Any persistent view needed for future spending must be validated against the commitment and existing consensus state. A matching digest authenticates the summary, while uniqueness and later reorganization still require the verified accounting view.

## Recovery and test gates

1. Establish the configured network and accepted pruning proof using existing consensus. Resolve the pruning point and a validated selected child. Reject a stale or unresolved selected-parent relationship.
2. Authenticate the child's body or approved inclusion proof against its committed header root. Extract the exact active version and expected digest from the authenticated carrier. Keep the imported checkpoint and claim stream untrusted throughout this step. Missing local replay and missing activated chain evidence both fail closed for issuance-required publication.
3. Verify the candidate context and conservation, recompute its event root from canonical records or an approved bounded witness, and compare with the independent digest. Reject wrong network or point, equal-total substitution, duplicate releases, stale ancestry and invalid liabilities. Retain enough authenticated state to validate successor claims and roll back above the accepted pruning point. An accounting view with historical uniqueness and rollback is still required for live activation.
4. Under existing authority and selected-chain guards, stage authenticated checkpoint and readiness in the shared RocksDB batch. Recheck the owner and chain selection before writing. If verification is cancelled, rejected or interrupted before commit, the previous durable accounting must remain usable under its authenticated owner. Reopen both records from the committed sequence; a stale selected binding must be unusable and replacement must be validated against the new selected evidence.
5. Run a true fresh-receiver fixture with no local replay prefix once the activation path exists. Include a valid nonzero commitment, negative evidence cases, interrupted writes, reopen, and selected-chain change. Until then, the local guarded test covers the fail-closed boundary only.

## Owner decision record and proposed v1 envelope

**Recommendation for review.** Put a single issuance field in an activated, versioned coinbase payload layout. This keeps the existing selected-child membership verifier and avoids adding a header field that every miner, serializer and peer must handle. Header placement gives a smaller proof. An accumulator can support incremental accounting but also needs a consensus-validated carrier and explicit rollback.

**Candidate bytes.** The legacy prefix is 51 bytes through the script-length byte, followed by the declared script bytes. Under a distinct activated layout, place exactly 34 bytes immediately after that script and before miner extra data. Use a two-byte little-endian version (v1 = `01 00`) and the 32 raw digest bytes. Parse only the versioned layout for activated blocks. The legacy layout retains its existing definition of the trailing bytes. The solver for activation, which block version or branch predicate selects the new layout, and the final payload size budget remain approval items. No scanning for a magic marker inside miner data. A short field, unknown version, wrong context, or digest mismatch fails validation on an activated branch. Miner data following the field never contributes an additional issuance field.

**Digest and ownership.** Use the existing v1 checkpoint preimage and claim/release hashing, including the network genesis hash and the selected parent's hash. The containing child's validated header and transaction Merkle root authenticate the field's placement. The field does not contain the child's hash. In parallel branches, each digest is checked against that child's own GHOSTDAG-selected parent and the authenticated accounting through that parent. Recomputing the digest after a selected-chain change uses the replacement ancestry and drops the displaced branch's obligations and reward-source usage. Arithmetic, event ordering, source uniqueness and release balance must be checked from locally validated settlement. Carry forward an authenticated representation of obligations and consumed reward sources for later claim validation. Merkle membership by itself cannot establish those transitions.

**Genesis and activation.** Pre-activation blocks carry the legacy payload and existing settlement rules. Genesis accounting must match the approved network's actual genesis allocation, with zero claims only where the genesis issues nothing. The first activated child needs an authenticated state through its selected parent, via full validated replay or an owner-approved migration checkpoint. Full validators need a deterministic way to handle first activation on competing branches and a reorganization back across the activation boundary. Software that does not enforce the new layout and accounting can accept invalid post-activation issuance, so deployment must include an explicit compatibility and upgrade policy. Keep the proposed 29B KCADE aggregate (21B primary, 8B finite tail) and any issuance schedule governed by separate activation.

**Fresh receiver.** The existing proof and header data establish a chain candidate under the node's configured PoW and bootstrap trust rules. The coinbase Merkle relation establishes that the chain committed to these bytes. It provides accounting assurance only if the receiver has an explicit trust basis for the activated chain's full validation, or additional authenticated evidence across the migration and historical window. Near activation and when local replay is missing, a trusted migration anchor or a stronger proof may be necessary even if the child body is present. A fresh receiver must reject missing, off-branch, or pre-activation evidence when issuance authentication is required. The imported checkpoint and claim stream remain untrusted until the digest, context, records, conservation and selected ownership agree.

**Decisions needed.** Approve (1) carrier and exact wire version/layout, (2) fork predicate and cross-activation reorg behavior, (3) genesis and migration accounting, (4) approved fresh-receiver trust/anchor policy and minimum historical proof, (5) old peer/miner compatibility and payload budget, and (6) separate private-network issuance activation parameters. Keep readiness on the opt-in local route until those decisions and the full-validator checks are in place.


## Implementation seams and inactive codec

- The `CoinbaseManager::expected_coinbase_transaction` builder owns transparent payout and parent liability handling. A future approved parser must distinguish the versioned extension from miner data. An approved builder would supply the digest for the selected parent from validated accounting, then hash the complete coinbase into the transaction Merkle root. Mining input cannot supply the expected digest.
- In `virtual_processor/utxo_validation.rs`, `verify_coinbase_transaction` uses the selected parent, its accepted DAA score and persisted developer accrual, plus validated merge-set rewards and non-DAA membership. It reconstructs the expected coinbase and compares its transaction hash. After approval, compute the independent selected-parent checkpoint at this boundary before verifying the candidate hash. A persisted complete per-source ledger with contextual replay is still required. The existing developer-liability row is only one input.
- `import_shielded_readiness::authenticated_selected_child_coinbase` already checks stored header, selected parent and full transaction Merkle root. The fresh receiver also needs a validated pruning proof and readiness input checks. The codec authenticates no bytes by itself, and its verifier expects a field obtained from an external authenticated source and consensus-derived pruning context.
- [Draft #60](https://github.com/DeepFriedBlockchains/KascadeNetwork/pull/60) adds a standalone candidate codec and fixed-size parse checks. It contributes no activation predicate, payload extraction, accepted block change, or migration behavior.

An independently validated replay from genesis gives the strongest transition evidence but removes the benefit of fresh pruning during bootstrap. An approved activation checkpoint binds the starting accounting when replay is unavailable, subject to the owner's trust and historical validity policy. A PoW-selected chain with the proposed field and ordinary Merkle proof proves body membership under the accepted chain selection. Accounting assurance in that case requires a policy for trusting activated full validation and the activation history. These are distinct approval decisions. Keep production issuance and the public network disabled pending those decisions and a passing end-to-end proof.


## Settlement verification and reorganization boundary

Draft #64 adds an inactive exact-field comparison against bounded independent replay. The selected history must begin at the configured network genesis and end at the selected parent. Recompute the canonical event commitment and paid/deferred totals from validated reward sources and developer releases; compare the result against the decoded bytes. An input checkpoint cannot supply the expected digest. Existing production builders and validators remain separate from this helper until an approved activation path can supply the full replay or an independently justified migration state.

For fresh recovery, select the header and pruning context using the approved chain and activation proof. Authenticate the child's body and its selected-parent link, then compare the independently verified historical state or approved migration anchor to the committed bytes. Rebuild the exact canonical claims and balance state required by subsequent full validation. Receiver readiness still requires committed UTXO, SMT, shielded and virtual-state verification. If selected ancestry changes, revalidate the child and reject an incompatible import. On a valid descendant fork above a fixed pruning point, the historical checkpoint for that common point remains compatible; an off-selected child is still unsuitable as the readiness witness. Production issuance remains disabled.
