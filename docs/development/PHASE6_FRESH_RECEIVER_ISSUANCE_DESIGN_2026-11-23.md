# Fresh pruned-receiver issuance authentication

November 23, 2026. Design for owner review. No consensus activation.

## Trust boundary

The current selected-child verifier checks the stored header, GHOSTDAG selected parent and transaction Merkle root before reading the coinbase. Header hashing commits to the transaction root, accepted-ID root, UTXO root and pruning point. The shielded verifier authenticates the shielded state root. None of these fields independently commits to historical minting, selected reward-source attribution or deferred developer liability. A peer can transport a checkpoint and a child body. The receiver must derive the expected issuance digest from independently accepted chain evidence before inspecting that checkpoint as an issuance proof.

Local replay is a separate source of evidence. It uses the locally validated settlement history and compares the supplied path to both directions of the persisted selected index under its authoritative guard. A retained local anchor can survive index pruning on that same node.

Recommend evaluating the coinbase extension first. The repository already verifies selected-child body membership and reads a commitment from that coinbase. Commit the digest for the **selected parent** (the target pruning point), through its settled state inclusive. Binding the containing block's own hash or that block's own settlement into the field would risk a hash cycle. At activation, validators must reconstruct the selected-parent digest from authenticated consensus accounting before accepting the child. An IBD proof authenticates selected chain evidence under the network's bootstrap assumptions; it does not replay historical settlement for the receiver. The owner must approve the trust assumptions used to cross activation, especially a node with no retained local history.

## Candidate v1 semantics

Reuse `IssuanceCheckpoint::commitment`. Its domain is the ASCII bytes `KASCADE/issuance-checkpoint/v1`, hashed using the existing `kaspa_hashes::TransactionHash` convention. Append network genesis hash, target pruning point hash and ordered event root as three fixed 32-byte values, then claim count, cumulative minted, paid and deferred as four unsigned 64-bit little-endian values. Amounts are in atomic units. This defines the digest preimage. The consensus wire envelope still requires approval. Specify an explicit version selector and 32-byte digest, require an exact canonical representation, reject missing, duplicate or unknown active versions, and forbid falling back to an unauthenticated version after activation.

The two existing leaf domains are `KASCADE/issuance-claim/v1` and `KASCADE/issuance-developer-release/v1`. Bind each leaf to the selected block hash and selected index. Order claims by selected index then source hash, followed by the single allowed release at that index. Claim leaves bind reward source, minted and paid. Release leaves bind the amount drawn from the developer liability. A release reduces deferred and increases paid by the same amount. Validate actual fee-only red-block accounting before constructing claims, and exclude fees from issued supply. Check unique sources, selected ancestry, at most one release per selected block, checked arithmetic, liability sufficiency, and minted = paid + deferred. The proposed aggregate limit is 29B KCADE, with 21B primary and 8B finite tail; the proposed phase budgets and cutoff require a separately validated schedule and activation. Any persistent view needed for future spending must be validated against the commitment and existing consensus state. A matching digest authenticates the summary, while uniqueness and later reorganization still require the verified accounting view.

## Recovery and test gates

1. Establish the configured network and accepted pruning proof using existing consensus. Resolve the pruning point and a validated selected child. Reject a stale or unresolved selected-parent relationship.
2. Authenticate the child's body or approved inclusion proof against its committed header root. Extract the exact active version and expected digest from the authenticated carrier. Keep the imported checkpoint and claim stream untrusted throughout this step. Missing local replay and missing activated chain evidence both fail closed for issuance-required publication.
3. Verify the candidate context and conservation, recompute its event root from canonical records or an approved bounded witness, and compare with the independent digest. Reject wrong network or point, equal-total substitution, duplicate releases, stale ancestry and invalid liabilities. Retain enough authenticated state to validate successor claims and roll back above the accepted pruning point. An accounting view with historical uniqueness and rollback is still required for live activation.
4. Under existing authority and selected-chain guards, stage authenticated checkpoint and readiness in the shared RocksDB batch. Recheck the owner and chain selection before writing. If verification is cancelled, rejected or interrupted before commit, the previous durable accounting must remain usable under its authenticated owner. Reopen both records from the committed sequence; a stale selected binding must be unusable and replacement must be validated against the new selected evidence.
5. Run a true fresh-receiver fixture with no local replay prefix once the activation path exists. Include a valid nonzero commitment, negative evidence cases, interrupted writes, reopen, and selected-chain change. Until then, the local guarded test covers the fail-closed boundary only.
